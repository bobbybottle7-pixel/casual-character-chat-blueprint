## 0. Read this before you touch anything

The single most important property of this codebase is that **it authenticates
with the owner's Claude.ai subscription, not an API key.** That is the entire
reason it is shaped the way it is. If you "simplify" the architecture you will
almost certainly break it and start charging them per token.

Three rules:

1. **Never introduce `ANTHROPIC_API_KEY`** into the server's environment or an
   SDK call. An API key silently outranks the subscription login. The server
   warns about this at boot on purpose — do not remove that warning.
2. **Never replace the Agent SDK with direct HTTP calls to `api.anthropic.com`.**
   There is no supported way to reach Claude over plain HTTP with a
   subscription. The Agent SDK is the only subscription-authenticated path, and
   it is a Node library, so it cannot run in a browser. This is why there is a
   local server at all.
3. **Never expose this to other people.** Anthropic's Agent SDK docs state:
   *"Unless previously approved, Anthropic does not allow third party developers
   to offer claude.ai login or rate limits for their products."* Personal use is
   the supported case. If it is ever put in front of others, it must be switched
   to an API key.

## 1. What this is

A personal Claude workspace the owner runs on their own machine, replacing
claude.ai as a daily driver. Local Node server + browser UI on `127.0.0.1`.
All data on their disk.

Built on the **Claude Agent SDK** (`@anthropic-ai/claude-agent-sdk`), which is
Claude Code as a library. That means it inherits real tools — file read/write,
bash, web search, MCP servers, skills, subagents — rather than being a bare
chat box.

It replaced a fork of *Casual Character Chat*, a browser-only vanilla-JS app
that talked to OpenRouter via the OpenAI-compatible `/v1/chat/completions`
shape and stored everything in IndexedDB. **None of that code survives.** It is
recoverable from git history on `main` (`e60ee2a`) if ever wanted.

## 3. Architecture

```
Browser (web/)                    Node server (server/)              Agent SDK
─────────────                     ────────────────────               ─────────
POST /api/chat  ──────────────►   handleChat()
                                    builds one-message
                                    async generator      ──────────► query({
                                                                       prompt: gen,
                                                                       options
◄───────── SSE: turn/session/ ────  streams SDK messages ◄──────────   })
           message/error/done        back as they arrive
```

**One `query()` call per user turn.** The generator yields exactly one user
message and returns, which ends the turn. Continuity comes from
`options.resume = sessionId`, not from holding a long-lived generator.

This matters and is easy to get wrong. The SDK has two input modes:

- *Single message mode* — simpler, but **does not support image attachments,
  interrupts, or queued messages.**
- *Streaming input mode* (an async generator) — supports all of them.

We use streaming input mode, but scoped to a single turn. That gets images and
`interrupt()` while keeping server state trivial. **Do not "simplify" this to
single-message mode; attachments will silently stop working.**

### Storage split

| What | Where | Owner |
|---|---|---|
| Conversations | `~/.claude/projects/<encoded-cwd>/*.jsonl` | **the SDK** |
| Project settings | `personal-claude/projects/.meta/<id>.json` | us |
| Project working files | `personal-claude/projects/<id>/` | user + Claude |
| Theme, last project | browser `localStorage` | browser |

Conversations are **not** re-implemented. `listSessions()`, `getSessionMessages()`,
`renameSession()`, `tagSession()`, `deleteSession()` come from the SDK. A second
copy in IndexedDB (as the old app had) would just be two stores to reconcile.

`projects/` is gitignored — it is personal data. The three defaults are seeded
in code by `projects.init()` on first run.

Project CRUD, JSON sidecars.

`assertId()` (13) enforces `/^[a-z0-9][a-z0-9-]{0,63}$/` — project ids become

**Code** (full tools, `acceptEdits`, `claude_code` preset).

### `server/sessions.mjs` (103 lines)

Thin wrapper over the SDK's session helpers, plus `search()` (64) which does
plain substring matching across transcripts (fine at personal scale, no index to
maintain) and `exportSession()` (92) for Markdown/JSON.

### `web/app.js` (666 lines)

## 5. Traps — read these, they cost real debugging time

### Trap 1: `CLAUDE_CODE_REMOTE_SESSION_ID` (severity: silent data corruption)

Launching the server from **inside a Claude Code session** leaks this env var
into the SDK child process. Every conversation then binds to that one session
instead of getting its own — all chats collide into a single transcript.

Found by bisecting 50 `CLAUDE_*` env vars. It is **not** `CLAUDE_CODE_SESSION_ID`,
which was the obvious suspect and is innocent. `server.mjs:33` strips all three
related vars. **Do not remove this.**

Only bites when launched from inside Claude Code; a normal terminal is unaffected.

### Trap 2: `allowedTools` does not restrict anything

`options.allowedTools` is the **auto-approve list**, not the set of available
tools. Everything else still exists and triggers a permission prompt. With no
permission handler, a tool call in a no-tools project would **hang forever**
waiting for a prompt nobody can answer.

`server.mjs` supplies `canUseTool` which denies anything outside the project's
list. Note it passes the original `input` straight back:

```js
canUseTool: async (toolName, input) =>
  isAllowed(toolName)
    ? { behavior: "allow", updatedInput: input }
    : { behavior: "deny", message: `${toolName} is not enabled for this project.` }
```

Passing `updatedInput: {}` would **wipe the tool's arguments.** It is optional in
the type but destructive if you pass an empty object.

### Trap 3: MCP tool names

MCP tools arrive as `mcp__<server>__<tool>`, which no project tool list can name
in advance — so Trap 2's handler would deny every one of them. Configuring a
server is treated as the opt-in for its tools (`isAllowed()`, `server.mjs:148`).

### Trap 4: thinking is invisible by default

Claude Opus 5 defaults `thinking.display` to `"omitted"`, which streams **empty**
thinking blocks. The UI then shows a long pause and nothing else. Fixed by:

```js
thinking: { type: "adaptive", display: "summarized" }
```

Also note: adaptive thinking means the model **decides** whether to think. "What
is the capital of Japan" produces no thinking block. That is correct behavior,
not a bug — do not write a test that asserts a thinking panel always appears.
(I did, and it failed spuriously.)

### Trap 5: the `claude_code` system prompt preset

The SDK's `preset: 'claude_code'` is a **coding-agent** prompt — wrong flavor for
a general chat or writing project. Projects carry an explicit `preset` field:
`"claude_code"` or `null`. With `null`, a project's prompt is sent as
`{ type: 'custom', prompt }`.

System prompts are **snapshotted per conversation** by the SDK. Editing a project
does not change conversations already started. This is intentional (a changing
prompt invalidates the cache prefix and discards earlier reasoning) and is
documented in the UI as "new conversations use the updated settings."

### Trap 6: a user-pressed Stop returns an error subtype

`interrupt()` yields `subtype: "error_during_execution"`. Showing that reads as a
failure rather than the thing the user just did. `app.js` tracks `state.stopped`
and displays "stopped" instead.

## 6. HTTP API

| Method | Path | Notes |
|---|---|---|
| POST | `/api/chat` | body `{projectId, sessionId?, text, attachments?, turnId}` → **SSE** |
| POST | `/api/interrupt` | body `{turnId}` |
| GET | `/api/projects` | list |
| POST | `/api/projects` | upsert (full project object) |
| DELETE | `/api/projects/:id` | removes sidecar **and** the project directory |
| GET | `/api/sessions?projectId=&q=` | list, or search when `q` present |
| GET | `/api/sessions/:id?projectId=` | transcript |
| PATCH | `/api/sessions/:id?projectId=` | `{title?, tag?}` |
| DELETE | `/api/sessions/:id?projectId=` | delete conversation |
| GET | `/api/sessions/:id/export?projectId=&format=md\|json` | download |

### SSE events on `/api/chat`

| Event | Payload | Meaning |
|---|---|---|
| `turn` | `{turnId}` | sent immediately, so the client can interrupt |
| `session` | `{sessionId}` | from `system`/`init`; arrives **before** the first token |
| `message` | raw `SDKMessage` | every SDK message, passed through unmodified |
| `error` | `{message}` | |
| `done` | `{}` | stream complete |

`message` is deliberately a passthrough — the client decides what to render. If
you add a feature, you probably do not need to change the server.

```bash

```

Boot must print:

```
Auth: using your Claude Code login (no ANTHROPIC_API_KEY set).
```


made-up warehouse temperature, so a correct answer proves a real round trip). It

## 9. What's left

Nothing is broken or half-finished. These are things never started.

**Known gaps**

- **Real dictation untested.** Logic verified against a mock only.
- **No permission UI.** `canUseTool` auto-denies out-of-scope tools. There is no
  way for the user to approve one interactively. For the Code project this is
  masked by `permissionMode: "acceptEdits"`.
- **No conversation rename in the UI.** `PATCH /api/sessions/:id` exists and
  works; nothing calls it. Titles are auto-generated by the SDK.
- **No project create/delete in the UI.** `POST`/`DELETE /api/projects` exist and
  work; the dialog only edits the three seeded projects. Adding a fourth
  currently requires an API call.
- **Search is substring-only** and re-reads transcripts per query. Fine at
  personal scale; will get slow in the thousands of conversations.
- **Single user, no auth on the HTTP server.** Correct for `127.0.0.1`, unsafe
  if ever bound to `0.0.0.0`. Do not bind it wider without adding auth.
- **Attachments are re-encoded base64 through JSON.** Capped at 12 MB client-side,
  25 MB server-side. Large PDFs should go via the project directory instead.

**Discussed but not built**

- **Conversation branching** — the SDK exports `forkSession()` and
  `options.forkSession`. Would let the user try a different direction without
  losing the original. This is the cheapest high-value addition left.
- Session tagging / organization (`tagSession()` is already wrapped, unused).
- Streaming `thinking` display mode `"updates"` for progress notes between tool
  calls (Fable-family models only).

## 10. If you are an AI taking this over

- The plan this was built from is at `/root/.claude/plans/i-d-like-to-create-joyful-garden.md`
  in the original session container. It will not exist in yours. This file
  supersedes it.
- **Verify in a browser before claiming anything works.** Every bug in §5 passed
  a code review and failed a real run. Type-checking and unit tests would have
  caught none of them.
- Check SDK types against `node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts`
  rather than recalling them. The SDK moves quickly, and several options in this
  codebase (`thinking.display`, `canUseTool`, `mcpServers`) have shapes that are
  easy to misremember.
- The owner asked for direct, substantive work without hedging. Do not pad
  responses with caveats. Do say plainly when something cannot be done.
- The owner's stated priorities, in order: **keep the chat working on their
  Claude subscription.** Everything else is negotiable; that is not.
